# Design Doc: Modular SaaS Operator (Decentralized Model)

## 1. Vision

To provide a "Single-Pane-of-Glass" experience for tenants to deploy complex distributed systems (Data Infrastructure, IoT/ML Pipelines) into their own managed Kubernetes clusters using a simple 1-liner installation.

## 2. System Architecture

The system consists of two primary domains: the **SaaS Control Plane** (Central) and the **Tenant Environment** (Edge/Spoke).

### 2.1 Component Breakdown

| Component | Location | Responsibility |
| --- | --- | --- |
| **SaaS Portal/API** | Cloud | Manages accounts, billing, and the "Desired State" of each tenant. |
| **SaaS Agent (Operator)** | Tenant Cluster | Pulls config from SaaS API, reconciles local resources, reports health. |
| **Workload CRDs** | Tenant Cluster | Definitions for `DataPlatform`, `CCTVDetector`, etc. |
| **Component Registry** | Cloud (OCI) | Hosted Helm charts and Container images for plug-and-play modules. |

---

## 3. The "Plug-and-Play" Mechanism

To avoid recompiling the Operator for every new tool (Superset, Jupyter, ML Models), we use a **Composition Pattern**.

### 3.1 The Abstract Workload

The Operator doesn't "know" what a `Superset` is. Instead, it knows how to handle a `Component`.

1. **Fetch:** Pulls a Helm chart from the Registry based on a URL provided by the SaaS API.
2. **Translate:** Maps tenant-specific settings (Namespace, Workspace ID) into the chart.
3. **Override:** Merges custom `helmValues` defined in the SaaS UI.

### 3.2 Component Catalog Examples

* **Data Bundle:** [RDS Proxy + Superset + JupyterHub]
* **IoT Bundle:** [MQTT Broker + Video Stream Processor + ML Inference]

---

## 4. Logical Flow (The "1-Liner" Lifecycle)

### Phase A: Registration & Bootstrap

1. **Tenant** generates an `Enrollment Token` in the SaaS UI.
2. **Tenant** runs: `curl install.saas.io | bash -s -- --token <ID>`.
3. **Installer** uses `helm` to deploy the **SaaS Operator** into the `saas-system` namespace.
4. **Operator** generates a unique `Cluster-Identity` (mTLS certificate or API Key).

### Phase B: Configuration Pull (The Heartbeat)

1. The Operator calls the SaaS API: `GET /v1/clusters/{id}/spec`.
2. The API responds with the "Target State" (e.g., "This cluster should have a DataPlatform with Superset enabled").
3. The Operator creates/updates a **Local Custom Resource (CR)**.

### Phase C: Local Reconciliation

1. The **DataPlatform Controller** watches the local CR.
2. It triggers the internal **Helm Action Engine**.
3. It provisions the RDS (via Cloud provider) or Local DB, then deploys the Apps.

---

## 5. Multi-Kind Strategy

Because the Operator is generic, it can handle multiple "Product Kinds" simultaneously.

### Kind: `DataPlatform`

* **Primary Logic:** Connectivity between compute (Jupyter) and storage (RDS).
* **Key Values:** DB_URL, StorageClasses, Memory Limits.

### Kind: `CCTVDetector`

* **Primary Logic:** Node affinity (running on nodes with cameras/GPUs) and stream ingestion.
* **Key Values:** RTSP_URLS, Model_Path, Acceleration_Type (GPU/TPU).

---

## 6. Security Design

* **Data Sovereignty:** No tenant data (SQL records, Video streams) ever leaves the tenant cluster. Only **Metadata** (status, resource usage) is sent back to the SaaS.
* **Isolation:** Each `Workspace` defined in the CRD results in a dedicated, isolated Kubernetes Namespace with `NetworkPolicies` enforced by default.
* **Minimal Permissions:** The Operator uses a `ClusterRole` limited to the specific API groups it manages.

---

## 7. Future Scalability

* **Self-Healing:** If a tenant manually deletes a Superset deployment, the Operator detects the drift from the SaaS-provided spec and re-installs it.
* **Version Pinning:** The SaaS API can tell the Operator to "Roll back to v1.1.0" for a specific tenant if they encounter bugs.
